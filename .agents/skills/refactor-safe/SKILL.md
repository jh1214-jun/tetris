# refactor-safe

## 진행 원칙

- 프로젝트 루트의 PRD.md와 README.md, 현재 구현 및 기존 테스트를 읽고 개선 대상과 보존할 기능·공개 API를 정리한다. HTML/CSS/JavaScript와 직접 파일 실행 구조를 유지한다.
- 변경 전에 관련 테스트 전체를 실행해 기준선을 기록한다. 실패가 있으면 직접 기능 수정으로 범위를 넓히지 말고 문제 표를 보고한다. 테스트가 없으면 현재 동작을 보존하는 최소 회귀 테스트부터 마련하고 통과시킨다. 실행할 수 없으면 미검증을 명시하고 리팩터링을 진행하지 않는다.
- 기능과 공개 API를 바꾸지 않는 작은 구조 개선을 직접 수행한다. 사용자의 기존 변경은 보존한다.
- 변경 후 같은 테스트 전체를 다시 실행한다. 회귀가 있으면 원인을 수정하거나 자신의 변경만 되돌린다. 통과 전에는 완료로 보고하지 않는다.
- 높은 심각도는 실행 불가·상태 손상·핵심 시나리오 차단, 중간은 일부 조건의 기능 오류·유지보수 방해, 낮음은 기능을 막지 않는 가독성·표현 문제로 분류한다.

## 점검 체크리스트

- [ ] 변경 전 기준선 — 통과: 관련 테스트 전체가 변경 전에 통과하고 명령·결과를 기록한다; 실패: 기존 실패가 있거나 테스트를 실행할 수 없는데 변경을 진행한다.
- [ ] 기능 보존 — 통과: 키 매핑, 점수, 하강 간격, 충돌·회전·종료·재시작 결과를 유지한다; 실패: 리팩터링에 규칙 변경이나 신규 기능이 섞인다.
- [ ] 공개 API 보존 — 통과: 공개 함수 이름·인수·반환 형식, 전역 진입점, DOM 연결 계약을 유지한다; 실패: 호출부 또는 테스트 계약을 깨뜨린다.
- [ ] 구조 개선 — 통과: 중복 제거나 책임 분리 목적에 필요한 최소 변경만 수행한다; 실패: 무관한 파일·설정 변경 또는 프레임워크·빌드 도구 도입이 포함된다.
- [ ] 변경 후 검증 — 통과: 동일한 관련 테스트 전체와 영향받는 화면·직접 실행 검증이 통과한다; 실패: 회귀가 남거나 테스트를 약화·삭제하여 통과시킨다.

## 보고 형식

각 체크리스트 항목의 판정과 근거를 요약한 뒤 발견한 문제를 다음 표에 심각도 순으로 보고한다. 항목에는 파일·위치와 재현 조건 또는 확인한 증거를 포함한다. 개선안은 실행 가능한 최소 조치로 적는다. 문제가 없으면 발견한 문제 없음이라고 적고 빈 예시 행을 만들지 않는다. 미검증 사항과 남은 검증 방법을 별도로 명시한다.

| 항목 | 심각도(높음 · 중간 · 낮음) | 개선안 |
|---|---|---|

추가로 변경 파일과 구조 개선 이유를 요약하고 아래 표에 실제 실행 명령, 통과·실패 수 및 종료 코드를 적어 변경 전후를 비교한다. 실행하지 않은 테스트를 통과로 보고하지 않는다.

| 검증 | 변경 전 명령·결과 | 변경 후 명령·결과 |
|---|---|---|
